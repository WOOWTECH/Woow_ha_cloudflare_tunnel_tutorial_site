第 9 章

管理 additional hosts

同一條 Tunnel 可以轉送其他內網服務，但「做得到」不代表「應該公開」。你會用一個 hostname 對一個 origin，落實最小暴露，並在移除路由後手動清掉殘留 DNS。

每多一個 host，就多一個入口

additional_hosts 讓本機管理型 Tunnel 把不同公開 hostname 送往不同內網服務，例如一個你自行維護的網站。附加元件會為清單中的 hostname 建立 Cloudflare DNS 路由，不必在家用路由器開入站連接埠。

但每新增一筆，也多一個需要更新、登入保護、監控與停用的外部入口。路由器、NAS、虛擬化平台與附加元件管理介面往往權限很高，不適合因為「偶爾方便」就直接公開。

真實變更：Config 的 Save & Restart 會改寫 Supervisor options 並重啟附加元件；本機管理型 Tunnel 啟動時也可能覆寫與 external_hostname 或 additional_hosts 同名的既有 DNS 記錄。操作前先核對名稱與原 DNS 用途。
示範環境保持唯讀：本教程沒有在截圖環境新增 host、儲存、重啟、授權或改 DNS。下列操作是給你在自己擁有與管理的環境中執行。

一筆路由有三個重點

欄位代表什麼正確概念
hostname外部使用者輸入的公開名稱例如 notes.example.com；不含協定、port 或路徑
serviceCloudflared 從附加元件所在網路連往 origin 的位址例如 http://192.168.1.20:8080；必須含 http:// 或 https://
disableChunkedEncoding關閉到 origin 的 HTTP chunked transfer encoding可選；只有 origin 確實不相容時才設 true

公開端通常用 HTTPS，不代表內部 service 一定要寫成 HTTPS；service 必須符合 origin 實際提供的協定與 port。若 origin 用自簽憑證，別隨便關閉驗證來繞過問題，本章也不加入未在附加元件 schema 中的進階鍵。

additional_hosts:
  - hostname: notes.example.com
    service: http://192.168.1.20:8080
範例不能照抄：網域、IP 與 port 只是格式示例。請填你自己控制的 hostname 與實際 origin；不要把陌生 IP 或管理後台照搬到設定。

安全新增一個 additional host

  1. 先寫下公開理由

    確認服務真的需要在家外使用，而不是只在家中 Wi-Fi 使用。若只是自己偶爾維護，優先考慮不公開的遠端存取方式；無法說清用途，就先不要新增。

  2. 檢查服務本身

    先在內網測試服務正常，完成更新、移除預設密碼、建立個人帳號並啟用可用的多因素驗證。Tunnel 只提供路徑，不會替 origin 修補漏洞或自動加入登入。

  3. 挑選未被使用的 hostname

    在 Cloudflare DNS 核對名稱目前沒有承載網站、郵件或其他用途。避免使用含姓名、住址或設備型號的名稱，也不要選一個既有重要 DNS 記錄來試。

  4. 確認 origin service 位址

    從 Cloudflared 附加元件可到達的角度填寫，例如 http://192.168.1.20:8080。不要填瀏覽器外部網址，也不要把 localhost 當成另一台主機；在附加元件容器中，它通常指向容器自己。

  5. 在 Config 新增一列

    開啟 Web GUI → Config → additional_hosts，新增 hostname 與 service。除非服務文件或實際錯誤明確需要，保持 disableChunkedEncoding 未啟用。

  6. 逐字核對後儲存並重啟

    先確認目前不是只能靠這條 Tunnel 遠端操作，再按 Save & Restart。這會寫入 Supervisor options 並重啟附加元件，不是預覽。等待 Dashboard 恢復 edge connection，查看 Logs 是否有設定、DNS 或 origin 錯誤。

  7. 先驗證身份保護，再做外網測試

    用手機行動網路開啟新的 https://hostname。預期看到正確服務與登入防護，不應直接進到管理畫面。若另設 Cloudflare Access，也要測試授權與服務本身的登入都正常。

  8. 記錄擁有者與移除方式

    在不含秘密的管理筆記記下 hostname、服務用途、負責人與定期檢查日期。也記下停用時要「從 Config 移除，再到 Cloudflare DNS 手動刪除記錄」。

秘密不能分享：不要公開 Cloudflare 授權網址、Tunnel token、憑證或完整 Logs。Logs 也可能含 hostname、內網 IP 與要求資訊；求助前只保留必要錯誤並遮蔽敏感內容。

哪些服務適合放進清單

服務情境建議理由
只供家中裝置使用不要新增沒有外部需求，就不該增加網際網路入口
有持續更新、強登入與明確外部需求的低權限服務完成風險檢查後可評估仍需最小權限、監控與定期更新
路由器、交換器或 Wi-Fi 管理頁不要直接公開一旦帳號或程式漏洞被利用，可能影響整個家用網路
NAS、虛擬化平台、容器管理後台預設不要直接公開通常能讀取大量資料或控制其他系統，後果高
沒有登入、已停止維護或仍用預設密碼的服務禁止新增Tunnel 不會補上應用程式缺少的身份驗證與修補
只需暫時測試設定明確到期時間，測完立即移除路由與 DNS避免忘記的長期入口
最小暴露：明列一個 hostname 對一個服務，比 catch_all_service 或萬用 DNS 更容易盤點。一般家庭不需要為了省幾列設定而開 catch-all。

公開前與公開後的安全清單

  1. 確認最小權限

    外部帳號只給使用功能所需權限，不使用 origin 的最高管理者帳號作日常登入。每位使用者應有自己的帳號，方便停權與追查。

  2. 保留雙層身份邊界

    服務本身的強密碼與多因素驗證不能拿掉。Cloudflare Access 可作為額外一層，但不是 origin 登入的替代品；也要先測試 App、API、webhook 或非瀏覽器用戶端是否相容。

  3. 限制新增數量

    逐筆檢查清單，移除沒有明確擁有者、用途或最近使用紀錄的 host。不要用 catch-all 或萬用 DNS 預先替未來服務留入口。

  4. 維持更新與監控

    定期更新 origin，檢查其登入紀錄與 Cloudflared Logs。分享 Logs 前遮蔽 hostname、內網 IP、帳號、token、Tunnel ID 與授權網址。

  5. 確認家用路由器仍未開埠

    使用 Tunnel 不需要新增入站 port forwarding。若服務過去曾直接開埠，確認沒有用途後依路由器程序關閉，避免同一服務同時有兩條外部入口。

  6. 準備立即停用程序

    發現異常時先從 additional_hosts 移除並重啟，再手動刪 Cloudflare DNS，必要時停用 origin、撤銷 session 或輪替憑證。不要只做其中一步。

每一個 host 都要單獨驗收

檢查測試方式通過條件
設定持久化重啟後重新整理 Config 與附加元件設定頁hostname、service 與預期相同
Tunnel 健康查看 Dashboard edge connections 與 Logs沒有循環重啟、DNS route 或 ingress 格式錯誤
正確 origin手機關 Wi-Fi，開啟完整 HTTPS hostname只顯示預期服務，不是 Home Assistant 或另一台設備
身份驗證使用未登入的私密視窗開啟先遇到預期登入或 Access 政策，不能直接進管理畫面
最小權限以一般外部帳號登入只能使用必要功能，不能意外取得管理權
不存在的名稱測試一個你沒有設定的子網域不應被意外的 catch-all 導向內部服務
本機服務家中網路直接使用原本內網位址原本操作仍正常，沒有因代理設定破壞服務
看到頁面不等於通過：你還要驗證未登入者被擋、權限足夠小、其他 hostname 不會誤入，以及停止服務時能完整移除入口。

Additional hosts 常見卡關

  1. 外部顯示 502 或 origin unreachable

    先在家中確認 origin 正常，再核對 service 的協定、IP 與 port。位址必須從附加元件可到達；另一台主機不能用 localhost 代替。不要靠關閉 TLS 驗證來掩蓋憑證或名稱問題。

  2. hostname 開到錯的服務

    逐字核對 hostname 是否與其他路由重複、service 是否貼錯，以及是否存在 catch-all。查看重啟後第一段路由日誌，但分享前遮蔽真實名稱與 IP。

  3. 設定完全不生效

    檢查是否設定了 tunnel_token。遠端管理型 Tunnel 會忽略本機的 additional_hosts；應在 Cloudflare Zero Trust 設定 public hostname 與 service。

  4. 特定應用回應中斷或格式異常

    只有 origin 文件或實際錯誤指出 chunked transfer encoding 不相容時，才對該筆嘗試 disableChunkedEncoding: true。上游 DOCS 以 WSGI／Proxmox 類情境為例；不要對所有服務一律開啟。

  5. 刪除 host 後 DNS 還在

    這是附加元件文件明示的限制。從清單刪除後，該 hostname 不再由這份 ingress 提供服務，但附加元件無法替你刪 Cloudflare DNS；請登入 Cloudflare DNS 手動刪除對應記錄並再次查核。

常見問題

移除一筆 additional host，就會自動刪掉 DNS 嗎？
不會。依附加元件 DOCS，路由不再提供服務，但 Cloudflare DNS 記錄無法由附加元件自動刪除；你必須到 Cloudflare DNS 手動清理。
要把 additional_hosts 全部清空，該怎麼表示？
使用空陣列 additional_hosts: []。儲存前確認影響，因 Save & Restart 會改寫 Supervisor options 並重啟附加元件；完成後仍要手動清除舊 DNS。
service 可以只填 192.168.1.20:8080 嗎？
不建議，也不符合文件範例。請明確包含 origin 實際協定，例如 http://192.168.1.20:8080 或正確設定的 HTTPS 位址。
Cloudflare Access 開了，就能把沒有密碼的服務公開嗎？
不要這樣做。Access 是可評估的額外保護層，不取代服務本身的身份驗證、修補與最小權限。也要測試 App、API 與 webhook 相容性。
可以用 additional_hosts 公開路由器或 NAS 管理頁嗎？
技術上可能能轉送，但本指南的保守建議是不要直接公開高權限管理介面。它們一旦被入侵，可能影響整個網路或大量資料；優先選擇不公開的管理方式。
disableChunkedEncoding 要預設打開嗎？
不用。它是針對不相容 origin 的可選設定。先保持關閉，只有文件或可重現錯誤確認需要時，才對單一 host 開啟並重新驗收。

官方來源與版本提示

欄位 schema、DNS 自動建立、刪除後需手動清理，以及 disableChunkedEncoding 行為，依 WOOWTECH 附加元件 DOCS；Supervisor 同步與 Save & Restart 依 Web GUI README。Tunnel ingress 與 origin 參數請查 Cloudflare Tunnel 官方設定文件，額外身份政策則查 Cloudflare Access 官方文件。

版本提示：Cloudflare 控制台選單名稱可能改版，所以 DNS 清理請以目前 Dashboard 中該 zone 的 DNS records 為準。無論介面文字如何變，移除 additional_hosts 並不等於刪除 DNS；這兩個動作都要驗收。
