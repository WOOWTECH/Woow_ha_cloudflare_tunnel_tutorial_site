用自然語言，讓 AI agent 幫你操作 Cloudflare

Cloudflare 有官方的 cloudflare/mcp-server-cloudflare，也有覆蓋全套資源的 REST API v4（api.cloudflare.com/client/v4/）。這本收錄 40+ 條實務提示詞，涵蓋 DNS、Tunnel、Access、Workers、Pages、WAF、Analytics 與故障排除，每一條都能直接複製丟給 Claude Code / Cursor / 任何支援 MCP 或 curl 的 AI agent，把手動操作 Dashboard 的時間拿回來。

這本是什麼

當你的 AI agent 有以下任一能力，這本就派上用場：

  • 裝了 Cloudflare 官方 MCP server（cloudflare/mcp-server-cloudflare）：agent 直接呼叫 tool 完成操作。
  • 會 curl / fetch REST API：任何模型只要能執行 shell 或 HTTP，都能打 https://api.cloudflare.com/client/v4/。
  • 會呼叫 Wrangler CLI：Workers/Pages 部署類提示詞會走這條路徑。

寫法上刻意避開「請生一段 curl」——直接描述目標讓 agent 挑正確工具，Dashboard 能做的它都做得到，包含批量、審計與跨資源自動化。

觀念：提示詞的價值不在「一字不差咒語」，而在「把目標、範圍、驗收、風險一次講清楚」。照抄能動，改成你 zone / account 的實情更好用。

怎麼用這些提示詞

  1. 準備 API Token（不是 Global Key）

    Cloudflare Dashboard → My Profile → API Tokens → 建一個範圍最小的 token（例如：Zone.DNS:Edit、Zone.Zone:Read）。

  2. 把 token 交給 agent

    用環境變數 CF_API_TOKEN（curl 走 Authorization: Bearer）；Wrangler 走 CLOUDFLARE_API_TOKEN；MCP server 依照 官方 README 設定。

  3. 複製一條提示詞

    把你的 zone 名稱、hostname、tunnel ID 替換進去，貼進 agent 對話。

  4. 保留「先報告再執行」的習慣

    會改資源的請求都寫成「先給我 dry-run 摘要，我確認再套用」。DNS / Access / WAF 誤改都會馬上影響對外服務——這句話最便宜。

安全：Token 不要貼進共享訊息、不要 commit 進 repo；發現外洩立刻在 Dashboard revoke。正式環境建議用 Scoped Token 限制到單一 zone、單一 permission group。

1 · DNS records 管理

Cloudflare 對 DNS 的操作走 /zones/{zone_id}/dns_records。批量整理 A/CNAME/TXT 用它比 Dashboard 快十倍。

列出 example.com zone 底下所有 DNS record，用 markdown 表格輸出 type / name / content / proxied / TTL。如果同一個 hostname 有多筆記錄，特別標註出來。

API: GET /zones/{zone_id}/dns_records。

幫我在 example.com 加一筆 CNAME：ha 指向 <tunnel-uuid>.cfargotunnel.com，proxied 開啟。加之前先確認同名 record 不存在，如果存在就先給我列出來我決定要不要覆蓋。

API: POST /zones/{zone_id}/dns_records；覆蓋走 PUT 帶 record_id。

把 example.com 底下所有 _acme-challenge.* 的 TXT record 列出來，超過 24 小時沒更新的直接刪掉（憑證早就簽完了）。刪之前先給我看要刪哪些。

批量清 Let's Encrypt 驗證殘留最實用。

幫我對 example.com 做一次 DNS 健檢：找出未使用 proxy 卻是 A / AAAA record（暴露源站 IP）、TTL 設 Auto 但實際 300 秒以下、以及指向已不存在的 tunnel / worker route 的 CNAME。用清單告訴我哪些該修。

我要把 old.example.com 302 轉址到 https://new.example.com/$1。用 Cloudflare 的 Bulk Redirect 或 Redirect Rules 幫我建，並確認轉址對 query string 也生效。

Bulk Redirect API 在 /accounts/{account_id}/rules/lists。

幫我為 example.com 導入 email 相關 DNS：SPF（v=spf1 include:_spf.google.com ~all）、DKIM（selector google）、DMARC（v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com）。同名 record 存在的話先給我列出來。

2 · Tunnel / hostname 設定

Cloudflare Tunnel 在 API 走 /accounts/{account_id}/cfd_tunnel；hostname 是 tunnel 內部的 ingress 配置。多主機路由這區最好用。

列出我 account 底下所有 Cloudflare Tunnels：ID、name、status、connections 數。狀態不是 healthy 的排前面，並附上 dashboard 直接跳轉的連結。

API: GET /accounts/{account_id}/cfd_tunnel。

建一條新的 tunnel 叫 home-lab，配置 ingress：ha.example.com → http://192.168.1.10:8123、z2m.example.com → http://192.168.1.10:8080、預設 catch-all 回 http_status:404。順便把對應的 DNS CNAME 建好。

我要把現有 tunnel home-lab 加一個 hostname nas.example.com，指向內網 https://192.168.1.20:5001，因為 NAS 用自簽憑證所以 originRequest.noTLSVerify 設 true。改完幫我列出完整 config 讓我確認。

tunnel home-lab 的所有 hostname 中，找出過去 7 天沒有流量的（用 Analytics API 交叉比對）。可能是我忘記刪的舊服務。列出來讓我決定要不要移除。

幫我為 tunnel home-lab 產生一份設定備份：全部 config、關聯的 DNS records、關聯的 Access apps 一起匯出成一個 JSON。方便我離站保存。

刪除 tunnel old-test-tunnel。刪之前先確認它沒有 active connections，並列出所有指向它的 DNS records 要一起清掉。全部搞定再回報。

3 · Access rules（Zero Trust）

Cloudflare Access 的 API 走 /accounts/{account_id}/access/apps 與 /access/policies。管家人白名單、SSO 政策這裡搞定。

幫我在 Zero Trust 為 ha.example.com 建一個 Access application，type 是 self-hosted。加一條 allow policy：只允許 email 是 me@example.com 或 wife@example.com，session 24 小時，identity provider 用 Google + One-time PIN。

列出我 Zero Trust 帳號下所有 Access apps：domain、type、associated policies、最近 30 天登入次數。從沒人登入過的排前面（可能是設好了但沒公開）。

在 ha.example.com 這個 app 底下加一條 policy：對路徑 /config/* 只允許主帳號，家人 email 白名單只能看 /lovelace/*。用 include + require 組合實作。改完給我 dry-run summary。

幫我建一個「臨時訪客」Access policy 給 ha.example.com：接受任意 email 走 OTP，但 session 只有 4 小時、只允許路徑 /lovelace/guest。我要給水電師傅遠端看狀態時用。

加一條國家限制到所有 Access apps：只允許來源國家 = TW，其他一律 block（連 Access 登入頁都不給看）。用 device posture rules 或 IP geolocation 實作，哪個穩就用哪個。

在 Access 幫我接 Google Workspace SSO：註冊一個 SAML / OIDC provider 給 @example.com 網域，之後所有 apps 預設用 Workspace 登入，家人 Gmail 用 OTP fallback。設定完給我測試連結。

4 · Workers deploy

Workers 走 wrangler deploy 或 API /accounts/{account_id}/workers/scripts/{name}。搭配 KV / D1 / R2 做 serverless 邊緣邏輯很好用。

列出我 account 底下所有 Workers scripts：name、routes、最近 24 小時 request 數、error rate。error rate > 1% 的排前面。

用 GraphQL Analytics API 抓 metrics。

幫我寫一個 Worker ha-webhook-proxy：接收 POST 請求，驗證 X-Auth-Token header，然後 forward 到我內網的 https://ha.example.com/api/webhook/xxx。設 route webhook.example.com/*。用 wrangler init + wrangler deploy。

我有一個 Worker 叫 image-optim，幫我加一個 KV binding 到現有的 KV namespace IMG_CACHE，並更新 wrangler.toml。改完部署到 preview，不要直接 push production。

為 Worker api-gateway 設定 secrets：UPSTREAM_TOKEN 從我的環境變數帶入、SIGNING_KEY 幫我產一個 32-byte random hex。用 wrangler secret put，不要落地到 wrangler.toml。

Worker api-gateway 過去 1 小時的 error log tail 給我看，只顯示 status >= 500 的。用 wrangler tail --format=json 抓，pretty-print 出來。

幫我把現有 Worker legacy-api 從 Service Worker 語法遷移到 Module Worker：addEventListener('fetch', ...) 改成 export default { fetch(...) }，順便升到 TypeScript。改完跑 wrangler dev 讓我本地測試。

5 · Pages 部署

Pages 用 wrangler pages deploy 直接推 build output，或走 API /accounts/{account_id}/pages/projects 管專案。適合靜態站 + Functions。

我剛剛 build 好在 ./dist，幫我用 wrangler pages deploy ./dist --project-name=my-blog 部署，並設 custom domain blog.example.com（如果 DNS record 還沒有就一起建）。

列出 Pages project my-blog 最近 10 次 deployment：id、branch、commit、狀態、建置時間。失敗的展開錯誤訊息第一行。

把 Pages project my-blog 上個 production deployment rollback：找出前一個 status=success 的 deployment，用 promote API 讓它成為 current。動作前先給我 diff 摘要。

建一個新的 Pages project docs-site：連 GitHub repo myorg/docs、build command npm run build、output dist、production branch main、preview 所有 PR。設 custom domain docs.example.com。

為 Pages project my-blog 加一個 Functions middleware，把所有 /admin/* 路徑丟給 Cloudflare Access 保護。順便產一個對應的 Access application 設定。

6 · Firewall / WAF rules

Firewall 走 /zones/{zone_id}/rulesets（新版）或舊的 /firewall/rules；Rate Limit 走 /rate_limits。用 Expression 語法描述條件。

在 example.com 加一條 WAF Custom Rule：(cf.threat_score gt 20 or ip.geoip.country in {"CN" "RU" "KP"}) and not http.request.uri.path contains "/api/webhook"，action = Managed Challenge。加之前先告訴我目前 zone 的 rule 順序會擺哪裡。

列出 example.com 目前所有 WAF rules（Custom + Managed + Rate Limits）：id、expression、action、last hit time、last 24h hits。命中 0 次的排最後，可能可以刪。

為 ha.example.com 加一條 rate limit：同一 IP 對 /auth/* 每分鐘超過 10 次就 block 1 小時。避免暴力破解 Home Assistant 登入。

開啟 example.com 的 Bot Fight Mode（免費層）與 Managed Rules 的 Cloudflare Managed Ruleset。啟用前告訴我可能會誤傷哪些合法工具（例如 Uptime monitor），我確認再開。

把 ha.example.com 的 SSL/TLS 模式設 Full (strict)，並開 Always Use HTTPS、Automatic HTTPS Rewrites、HSTS（max-age 6 個月，含 subdomain）。改之前先確認 origin 憑證有效。

建立一個 IP Access Rule 白名單：把家裡固定 IP 1.2.3.4 加成 whitelist，並將公司 IP 5.6.7.8/32 也加進來。之後 WAF 規則可以引用這個 list。

7 · Analytics 查詢

Cloudflare 分析走 GraphQL Analytics API（/graphql）。跟 Dashboard 一樣的資料，但可以 script / 定時抓。

用 GraphQL Analytics API 撈 example.com 過去 24 小時的 request 統計：total requests、cached requests、cache hit ratio、bandwidth、top 10 status codes。輸出成 markdown 表格。

列出過去 7 天 ha.example.com 的 Access 登入紀錄：user email、時間、來源 IP、國家、user agent。可疑（半夜、非常用 IP、失敗次數多）的標記出來。

給我 example.com 過去 30 天的 WAF 攻擊摘要：top 10 blocked countries、top 10 blocked rules、被觸發最多的 URL path。用一段 Chinese narrative 加表格輸出，適合貼進客戶月報。

Worker api-gateway 過去 6 小時每 15 分鐘的 invocation 數、CPU time p50/p99、error rate 折線資料，輸出成可以直接畫圖的 JSON（timestamp, value）。

跨所有 zone 查：哪些 zone 過去 7 天 5xx error rate > 5%？列表按 error rate 排。error 詳情前 5 條的 sample trace 也一起帶。

8 · 故障排除

Tunnel 掉線、DNS 沒生效、Access 一直退登、Worker 5xx——先讓 agent 做完診斷再動手。

ha.example.com 打開一直 502。幫我做一次完整診斷：DNS 記錄是否正確、tunnel connections 狀態、對應的 ingress config、origin 是否 reachable、最近 10 分鐘 Cloudflare edge 錯誤 log。給我一份 markdown 診斷報告。

Cloudflare 上顯示 tunnel home-lab 是 degraded，只有 1 個 edge connection 而不是 4 個。幫我查：cloudflared 版本是否過舊、edge_ip_version 設定、家裡網路是否有 QUIC / UDP 阻擋。給修復建議。

我剛剛改了 ha.example.com 的 CNAME，dig 出來還是舊值。幫我：
1) 檢查 Cloudflare 上的 record 是否已更新
2) 從多個 public DNS resolver（1.1.1.1, 8.8.8.8, 9.9.9.9）測試 propagation
3) 檢查 TTL 設定是否過長。

家人回報 ha.example.com 一直被 Access 踢出來重登。幫我查最近 24 小時的 Access log 找他 email 的登入紀錄，看是不是 session duration 設太短、或觸發某條 require rule。

Worker api-gateway 從凌晨開始 5xx 暴增。幫我 wrangler tail 抓最近 15 分鐘 error，找出重複最多的 exception 訊息，並在 dashboard 看是不是撞到 CPU time / subrequest 上限。

example.com Universal SSL 一直卡在 pending。幫我：
1) 列出 zone status 與 nameserver 設定
2) 查 CAA record 是否阻擋 Cloudflare / Let's Encrypt
3) 確認 root 與 www CNAME 是否都指到 Cloudflare。修復完主動幫我重新觸發簽發。

提示詞寫法小抄

Cloudflare 資源改一下就影響外部服務——比家用自動化更需要「防呆」。看完 40+ 條，套路只有這五招：

這樣講不要這樣講為什麼
指定 zone / account：「在 example.com zone 底下…」 「幫我加一筆 DNS」 Cloudflare token 常有多 zone 權限；不指定 agent 會猜錯。
先 dry-run：「先給我 diff / 預覽，我確認再套用」 「直接改 production」 DNS / WAF 誤改馬上影響對外服務。
驗收條件：「跑完 curl 一次 ha.example.com 確認 200」 省略驗證 不驗證等於在猜；agent 願意跑就讓它跑。
限制範圍：「只針對 /config/* 這一條 path」 「全部路徑套用」 Access / WAF 影響面越大越容易誤傷。
失敗處理：「同名 record 存在時先讓我選要不要覆蓋」 假設一切順利 Cloudflare API 對重複資源會直接報錯或覆蓋，先想好。

常見問題

Cloudflare 官方 MCP server 在哪？現在能用嗎？
Cloudflare 官方 cloudflare/mcp-server-cloudflare 提供 Workers、KV、R2、D1、Analytics 等 tool；本站的 Claude 環境也裝了 cloudflare-platform-mcp。若你的 agent 不支援 MCP，直接用 curl 打 REST API 效果一樣。
Global API Key 跟 API Token 差在哪？
Global API Key 是「萬能鑰匙」，權限等同帳號本人；API Token 可以指定 scope（哪個 zone / account、哪些 permission）。永遠用 Token，不要用 Global Key。生一個 token → 只勾當前任務需要的權限 → 綁 IP filter 更安全。
Wrangler 跟 curl API 什麼時候該用哪個？
Workers / Pages 部署與 tail 用 Wrangler（有 hot-reload、bindings 管理）；DNS / Access / WAF / Analytics 之類的資源操作用 REST API（更精細、可 script）。Cloudflare MCP server 大部分包裝的是 REST。
agent 亂改我 zone 怎麼辦？
兩層保險：1) Token 只給最小 scope，不給的就打不到；2) 提示詞永遠寫「先給我 diff / 預覽，我確認再套用」。誤操作真的發生了，Cloudflare Audit Logs（Enterprise）或 Dashboard 的 change history 可以還原大部分設定。
怎麼在 CI 裡自動化這些提示詞？
CI 就別用 LLM 中介了——把提示詞落地成 Terraform（cloudflare/cloudflare provider）或直接 curl script。LLM 適合互動探索與一次性操作；規律變更用 IaC 才穩定可 review。
