Chapter 1

Before you start: draw the security boundary first

First confirm that your Home Assistant can run add-ons and that your domain is served by Cloudflare, then decide who is allowed to connect from outside. This chapter is inventory and planning only. It changes nothing in the Cloudflared options, in Cloudflare, or on your home router.

Plan first, so you don't open the wrong door

Cloudflare Tunnel lets the cloudflared in your home dial out to Cloudflare, so you do not have to set up inbound port forwarding on your router. That removes one common risk, but it does not turn the URL itself into a private space: once you publish a public hostname, people on the internet may still reach the entrance on the Cloudflare side. What protects you from there on is the Home Assistant sign-in and the Cloudflare access policy you choose.

What you get from this chapter: a preparation checklist, a decision on which tunnel management mode to use, and a clear security line around what you are not doing yet. Gathering the facts first and only then moving on to install and configuration is far safer than clicking and guessing.
Read-only disclosure: the capture and verification environment for this guide was used only to look at the interface read-only. Nothing was saved, restarted or authorized, and no tunnel was changed. The text describes what each action does when you really run it, which does not mean that environment was modified.

Think of the tunnel as a line dialed out from your house

A traditional setup usually has the router waiting on a fixed port for a request from outside. With Cloudflare Tunnel, the connector at home opens the connection instead, and it is outbound only. An external request reaches Cloudflare first, then travels along the established tunnel to the origin service you named explicitly. So you do not have to open an inbound port for Home Assistant on your router, and you do not need a publicly routable home IP.

Tell the two entrances apart first: the Web GUI inside Home Assistant is the Ingress for managing the add-on. The https://ha.example.com you build later is the entrance for reaching Home Assistant remotely. Do not treat the Web GUI admin page as a service to expose.

Six steps to a pre-flight inventory

  1. Confirm your Home Assistant installation type

    On the Home Assistant system information page, confirm that your installation can run Supervisor-managed add-ons. The official Home Assistant docs currently cover add-ons under the Home Assistant OS workflow. If there is no Apps store under "Settings", do not force these install steps onto your system; look up your installation type first.

  2. Confirm your hardware architecture

    The add-on config in this repository currently lists aarch64 and amd64. If your system architecture is neither, adding the repository may still leave you with no installable version; stop and check the project's release information first.

  3. Get your Cloudflare account and domain ready

    Confirm that you can sign in to the right Cloudflare account, and that the domain you plan to use already has its DNS served by Cloudflare. Write down only the public name of the domain. Never put an account password, an API token or a tunnel token into shared notes.

  4. Pick a hostname that is not already in use

    Plan a full subdomain, for example ha.example.com. Check in Cloudflare DNS whether it already serves a website, mail or something else; when the locally managed mode starts, the docs warn explicitly that a matching external_hostname or additional_hosts DNS record may be overwritten.

  5. Decide between locally managed and remotely managed

    If this is your first time and you want the add-on to create the tunnel and the DNS route, the locally managed mode the docs recommend is usually the right choice. Only weigh up the remotely managed mode if you already manage tunnels and public hostnames in the Cloudflare dashboard; it uses tunnel_token, and the other local settings in the add-on are ignored.

  6. Write down your stopping point and how to roll back

    This chapter stops at "the facts are confirmed": no tunnel is started, nothing is authorized, no DNS is changed. Check the date of your existing Home Assistant backup and how to restore it, and confirm that you can still sign in from your home network using the local URL. If you have no usable backup, make creating one a required item before any real change.

Do not share secrets: the Cloudflare authorization URL, the tunnel token, the session cookie, and any log that may contain them or your account, hostname, tunnel ID or IP must never be posted to a public forum. When you ask for help, quote only the error you have to show, and redact it first.

Do not mix the two modes: once tunnel_token is filled in for the remotely managed mode, the docs state that the add-on's other settings are ignored. Seeing the fields still on the screen does not mean they control the routes in the Cloudflare dashboard.

If you are still unsure, pick locally managed and plan a single Home Assistant hostname. Do not add the router, the NAS, a camera or an admin interface on day one. The fewer services there are, the clearer the acceptance check and the troubleshooting.

Chapter acceptance check: all six answers must be yes

  1. You can see add-on management

    You have confirmed that your Home Assistant installation type and its interface can manage add-ons, not just ordinary integrations.

  2. The hardware architecture is supported

    Your system is one of the architectures the current add-on config lists, aarch64 or amd64; if it is not, you have stopped before installing.

  3. Cloudflare DNS permissions are right

    You can manage the right zone under the right account, and the hostname you picked has no existing use that must not be overwritten.

  4. You picked exactly one mode

    You have deliberately chosen locally managed or remotely managed, and you know which side manages the hostname and the routing in each case.

  5. You still have a local fallback

    You can sign in to Home Assistant from your home network, and you have checked your existing backup and how to restore it; if you have no usable backup, stop at this chapter and make no real change.

  6. Nothing has changed yet

    You have only taken inventory. Reading this chapter has not made you save a setting, start the add-on, complete a Cloudflare authorization, or change DNS or a router rule.

Move on only when everything passes: the next chapter is where you add the third-party repository and install the package; creating the tunnel and authorizing it come in later chapters.

Common planning pitfalls

  1. You cannot find Apps under "Settings"

    Check the installation type on the system information page first. Add-ons need a Supervisor-managed environment, and Home Assistant Container is not installed through this add-on store flow. Do not run some unknown container command just because the name looks similar.

  2. You do not know your CPU architecture

    Read the architecture from the Home Assistant system information, then compare it with the project's config.yaml, which lists aarch64 and amd64. Do not guess from the device's product name alone.

  3. The domain is not on Cloudflare DNS

    Set up the DNS delegation correctly between your registrar and the Cloudflare zone first, then wait for the status to go normal. Typing the subdomain into the add-on does not replace the domain's Cloudflare DNS setup.

  4. The hostname you picked already has a DNS record

    Find out what that record serves. If it is still in use, pick a new hostname; do not let the locally managed flow overwrite the record of an existing website, mail service or anything else.

  5. You do not know which tunnel mode to choose

    With no prior experience managing a Cloudflare Tunnel, follow the project docs and choose locally managed. Choose remotely managed only once you have created a remotely managed tunnel and understand where the token and the dashboard routing responsibilities sit.

Before you start FAQ

Does using a tunnel mean I don't need the Home Assistant sign-in at all?
No. A tunnel solves the connection path; it does not replace Home Assistant authentication. A public hostname should still keep the Home Assistant sign-in in front of it, and if your risk profile calls for it, weigh up an Access policy by following the official Cloudflare docs.
Do I have to have a domain of my own?
The first-run setup docs for this add-on's locally managed mode say you need a domain whose DNS is served by Cloudflare, and that you settle on a full hostname. Do not treat a temporary test URL or somebody else's domain as a real solution.
Do I need a static public IP, or to open 8123 on the router?
Cloudflare Tunnel has cloudflared open the connection outbound, so it does not require a publicly routable source IP, and you should not add inbound port forwarding for Home Assistant for this guide.
Does the Web GUI behave differently from the original Cloudflared add-on?
The WoowTech README states that the tunnel core, the Supervisor options schema and the log output are inherited from upstream; what is new is the Ingress Web GUI. With a completely blank configuration, this fork keeps the GUI reachable while the tunnel stays stopped, which makes the first setup easier.
Can I send the authorization URL or the token to whoever is setting this up for me?
No. Treat the authorization URL, tunnel_token, sign-in details and any log containing secrets as sensitive data. If you want someone to help, share your screen and carry out the sensitive steps yourself, or hand over a redacted summary of the error.
