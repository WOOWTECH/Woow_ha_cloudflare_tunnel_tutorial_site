Chapter 9

Manage additional hosts

The same tunnel can forward other services on your local network, but "you can" does not mean "you should make it public". You will map one hostname to one origin, apply minimal exposure, and clear the leftover DNS by hand after you remove a route.

Every extra host is another way in

additional_hosts lets a locally managed tunnel send different public hostnames to different services on your local network — a site you maintain yourself, for example. The add-on creates a Cloudflare DNS route for each hostname on the list, so you do not have to open an inbound port on your home router.

But every entry you add is one more external entrance to keep updated, protect with a sign-in, monitor and eventually shut off. Routers, NAS boxes, virtualization platforms and add-on admin interfaces usually carry high privileges, so "handy once in a while" is not a good reason to expose them directly.

A real change: the Config page's Save & Restart writes to Supervisor options and then restarts the add-on. A locally managed tunnel may also overwrite an existing DNS record that shares a name with external_hostname or with an entry in additional_hosts when it starts. Check the names, and what the existing DNS records are for, before you act.
The demo environment stays read-only: for this guide we added no host, saved nothing, restarted nothing, authorized nothing and changed no DNS in the screenshot environment. The steps below are for you to run in an environment you own and manage.

Three things matter in one route

FieldWhat it meansThe right idea
hostnameThe public name an outside user typesFor example notes.example.com; no protocol, port or path
serviceThe address cloudflared uses to reach the origin from the network the add-on sits onFor example http://192.168.1.20:8080; it must include http:// or https://
disableChunkedEncodingTurns off HTTP chunked transfer encoding to the originOptional; set it to true only when the origin genuinely cannot handle it

The public side usually runs over HTTPS, but that does not mean the internal service has to be written as HTTPS too; service must match the protocol and port the origin actually serves. If the origin uses a self-signed certificate, do not casually turn verification off to get around it, and this chapter does not add advanced keys that are absent from the add-on schema.

additional_hosts:
  - hostname: notes.example.com
    service: http://192.168.1.20:8080
Do not copy the example verbatim: the domain, the IP and the port only show the format. Fill in a hostname you control and your real origin; never paste an unfamiliar IP or an admin back end into the configuration.

Add one additional host safely

  1. Write down why it has to be public

    Confirm that the service really has to be used away from home, not only on your home Wi-Fi. If you only maintain it yourself now and then, prefer a remote-access method that is not public; if you cannot state the purpose clearly, do not add it yet.

  2. Check the service itself

    Test the service on your local network first, apply its updates, remove default passwords, create individual accounts and turn on multi-factor authentication where it is available. A tunnel only provides the path; it will not patch the origin's flaws or add a sign-in for you.

  3. Pick a hostname that is not in use

    Check in Cloudflare DNS that the name is not currently carrying a website, mail or any other purpose. Avoid names that contain a person's name, an address or a device model, and do not experiment on an existing DNS record that matters.

  4. Confirm the origin service address

    Fill it in from the point of view of what the Cloudflared add-on can reach, for example http://192.168.1.20:8080. Do not enter the external URL you open in a browser, and do not treat localhost as another machine; inside the add-on container it usually points at the container itself.

  5. Add one row on the Config page

    Open the Web GUI → Config → additional_hosts and add the hostname and the service. Leave disableChunkedEncoding off unless the service documentation or a real error clearly calls for it.

  6. Check every character, then save and restart

    Make sure this tunnel is not your only way to work remotely right now, then press Save & Restart. It writes to Supervisor options and then restarts the add-on; it is not a preview. Wait for the Dashboard to get its edge connection back, then read the Logs for configuration, DNS or origin errors.

  7. Verify the sign-in protection first, then test from outside

    Open the new https://hostname over mobile data on your phone. You should see the right service behind its sign-in protection, not land straight on an admin page. If you also set up Cloudflare Access, test that both the authorization and the service's own sign-in work.

  8. Record the owner and how to remove it

    In admin notes that hold no secrets, write down the hostname, what the service is for, who is responsible for it and the date of its regular review. Also write down that retiring it means "remove it from Config, then delete the record by hand in Cloudflare DNS".

Secrets are never shared: never publish the Cloudflare authorization URL, the tunnel token, credentials or a full set of Logs. Logs can also contain hostnames, local IP addresses and request details; before you ask for help, keep only the errors you need and redact anything sensitive.

Which services belong on the list

Service scenarioRecommendationWhy
Used only by devices at homeDo not add itWith no external need, you should not add an entrance from the internet
A low-privilege service that is kept updated, has a strong sign-in and a clear external needWorth considering once the risk check is doneIt still needs least privilege, monitoring and regular updates
A router, a switch or a Wi-Fi admin pageDo not expose it directlyOnce an account or a software flaw is exploited, your whole home network can be affected
A NAS, a virtualization platform or a container admin back endDo not expose it directly by defaultThese can usually read large amounts of data or control other systems, so the consequences are severe
A service with no sign-in, no maintenance, or still on its default passwordNever add itA tunnel will not supply the authentication and patches the application is missing

Minimal exposure: listing one hostname to one service explicitly is easier to take stock of than catch_all_service or wildcard DNS. An ordinary household has no reason to turn on a catch-all just to save a few lines of configuration.

Security checklist before and after going public

  1. Confirm least privilege

    Give an external account only the permissions the feature needs, and do not use the origin's top administrator account for everyday sign-in. Every user should have their own account, so access is easy to revoke and activity is easy to trace.

  2. Keep both identity boundaries

    The service's own strong password and multi-factor authentication must not be removed. Cloudflare Access can add a layer on top, but it does not replace the origin's sign-in; test first whether apps, APIs, webhooks and other non-browser clients still work with it.

  3. Limit how many you add

    Go through the list entry by entry and remove any host without a clear owner, a clear purpose or a recent record of use. Do not use a catch-all or wildcard DNS to reserve an entrance for some future service.

  4. Keep updating and monitoring

    Update the origin regularly and review its sign-in records along with the Cloudflared Logs. Before you share Logs, redact hostnames, local IP addresses, accounts, tokens, the tunnel ID and the authorization URL.

  5. Confirm your home router still has no open port

    Using a tunnel does not require new inbound port forwarding. If the service once had a port opened directly, confirm it is no longer needed and close it the way your router expects, so one service does not end up with two external entrances at once.

  6. Have an immediate shutdown procedure ready

    When something looks wrong, first remove the entry from additional_hosts and restart, then delete the Cloudflare DNS record by hand, and where necessary stop the origin, revoke sessions or rotate credentials. Do not stop after one of those steps.

Seeing the page is not the same as passing: you still have to verify that a signed-out visitor is blocked, that permissions are small enough, that other hostnames do not stray in, and that you can remove the entrance completely when you retire the service.

Common additional hosts pitfalls

  1. The outside shows 502 or origin unreachable

    Check at home first that the origin is working, then verify the protocol, IP and port in service. The address must be reachable from the add-on; another machine cannot be reached as localhost. Do not paper over a certificate or name problem by turning TLS verification off.

  2. The hostname opens the wrong service

    Check character by character whether the hostname duplicates another route, whether the service value was pasted in wrong, and whether a catch-all exists. Read the first routing entries in the log after the restart, but redact the real names and IP addresses before you share it.

  3. The configuration has no effect at all

    Check whether tunnel_token is set. A remotely managed tunnel ignores the local additional_hosts; the public hostname and the service belong in Cloudflare Zero Trust instead.

  4. One app's responses cut off or come back malformed

    Only when the origin's documentation or a real error points at incompatible chunked transfer encoding should you try disableChunkedEncoding: true on that one entry. The upstream DOCS use WSGI / Proxmox style situations as the example; do not turn it on for every service.

  5. The DNS record is still there after you delete the host

    This is a limit the add-on documentation states plainly. Once you delete the entry, that hostname is no longer served by this ingress, but the add-on cannot delete the Cloudflare DNS record for you; sign in to Cloudflare DNS, delete the matching record by hand, and check again.

FAQ

If I remove one additional host, does the DNS record get deleted automatically?
No. According to the add-on DOCS the route stops serving, but the Cloudflare DNS record cannot be deleted automatically by the add-on; you have to clean it up by hand in Cloudflare DNS.
How do I write additional_hosts when I want to clear it completely?
Use an empty array, additional_hosts: []. Confirm the impact before you save, because Save & Restart writes to Supervisor options and then restarts the add-on; afterwards you still have to clear the old DNS by hand.
Can service just be 192.168.1.20:8080?
We do not recommend it, and it does not match the examples in the documentation. Spell out the protocol the origin actually serves, for example http://192.168.1.20:8080 or a correctly configured HTTPS address.
With Cloudflare Access turned on, can I expose a service that has no password?
Do not do that. Access is an extra layer worth considering; it does not replace the service's own authentication, patching and least privilege. Test app, API and webhook compatibility as well.
Can I use additional_hosts to expose a router or a NAS admin page?
Technically it can probably be forwarded, but the conservative advice in this guide is not to expose a high-privilege admin interface directly. Once one is broken into, it can affect your whole network or a large amount of data; prefer a management method that is not public.
Should disableChunkedEncoding be on by default?
No. It is an optional setting for origins that cannot handle it. Leave it off, and turn it on for a single host only when the documentation or a reproducible error confirms it is needed, then run the acceptance check again.

Official sources and version notes

The field schema, the automatic DNS creation, the manual cleanup needed after a deletion and the behavior of disableChunkedEncoding all follow the WoowTech add-on DOCS; Supervisor synchronization and Save & Restart follow the Web GUI README. For tunnel ingress and origin parameters see the official Cloudflare Tunnel configuration docs, and for extra identity policies see the official Cloudflare Access docs.

Version note: menu names in the Cloudflare dashboard can change between releases, so for DNS cleanup defer to the DNS records shown for that zone in the dashboard today. No matter how the interface wording changes, removing an entry from additional_hosts is still not the same as deleting the DNS record; both actions need their own acceptance check.
