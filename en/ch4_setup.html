Chapter 4

The Setup wizard: choose your management mode first

Tell locally managed and remotely managed apart first, then look at what each step of the Setup wizard stands for. You will finish a configuration plan and know when a write and a restart happen, without mixing the two modes together.

Setup is a progress tracker, not a second set of settings

Once Chapter 3 has walked you through the four pages, Setup is the one that is easiest to misread: it looks like a form that collects everything from you, when its main job is to watch the progress of the first start. The real values still live in Supervisor options, written and read by Config and by the Home Assistant add-on configuration page; the tunnel login, the tunnel creation, the DNS route and the connection work all run automatically from those values when the add-on starts.

Choosing the management mode before you begin matters. In locally managed mode (local-managed) the add-on creates the tunnel, keeps the local account certificate and builds the routes from your options; in remotely managed mode (remote-managed) the Cloudflare dashboard is in charge and the add-on only uses tunnel_token to connect. Mix the two, the way you would confuse a courier by handing over two addresses at once, and the hostname fields are still on screen while nothing actually uses them.

Scope of this walkthrough: in the capture environment for this guide we only read Setup. We saved nothing, restarted nothing, authorized nothing with Cloudflare, created no tunnel and changed no DNS. The real steps below apply only to a Home Assistant you control yourself, with a local fallback already in place.
Remember this first: Save & Restart writes to Supervisor options and then restarts the add-on; it is not a preview button and it is not a next button. The restart interrupts the Web GUI and the tunnel for a while, and it can also trigger authorization, tunnel creation and a DNS route.

Reading the screen: when Setup detects a token it shows the remote-managed tunnel notice and explains that the four local steps below do not apply. The Mode card on the Dashboard also shows token or local; that is a hint about the mode, not proof that the tunnel is connected.
Switching modes is not switching tabs: adding or removing tunnel_token changes who is responsible, and it only takes effect after a save and a restart. While an existing tunnel is working, do not switch back and forth just to see what the screen does.

Seven steps to plan before Setup

  1. Confirm your local fallback and your maintenance window

    Open the Home Assistant local URL on your home Wi-Fi and sign in, so you know you are not relying on the current tunnel alone. If you are away from home, if nobody there can help you, or if the people you live with are using the current connection right now, stop at planning and restart nothing.

  2. Check your Cloudflare account and your DNS zone

    Sign in to your own Cloudflare account, confirm the domain you intend to use really is on Cloudflare DNS, and that you have permission to manage the right zone. If the hostname you have in mind already serves a website, mail or anything else, pick a new name, because the locally managed flow can overwrite a matching DNS record.

  3. Choose one mode only

    With no existing remote-managed tunnel, choose locally managed, as the project DOCS recommend. Choose remotely managed only if you have already created the tunnel in Cloudflare, know where its public hostnames are maintained, and hold that tunnel's token; write the choice down in a maintenance note that carries nothing sensitive.

  4. Finish the Home Assistant reverse proxy configuration

    If you are going to put Home Assistant behind the tunnel, back up configuration.yaml locally first, then merge the minimal configuration below into your existing http: block, following the project DOCS. A standard Supervisor add-on setup uses the Docker network range the documentation specifies; on a non-standard installation, do not copy it verbatim — judge from your actual Home Assistant log.

    http:
  use_x_forwarded_for: true
  trusted_proxies:
    - 172.30.33.0/24

    Use the Home Assistant configuration check to confirm the YAML is sound, schedule one Home Assistant restart, and verify again that you can sign in on the local URL. This step is a real change; if you have no local fallback, stop here.

  5. Enter the minimal local route in Config

    In locally managed mode, fill in exactly one external_hostname that is genuinely yours the first time, for example ha.example.com; check that it sits in the right Cloudflare zone and that it carries no website, mail or other existing service. Keep additional_hosts empty, and turn on no catch-all, no wildcard DNS, and no router or NAS admin page.

  6. In remote mode, prepare only the token and the Cloudflare routes

    Take the token from the tunnel you created in the Cloudflare dashboard and keep it in a password manager; the public hostname and the origin service are set on the Cloudflare side as well. Do not expect the add-on's local options to manage the same routes at the same time.

  7. Go back to Setup and check the expected path

    In locally managed mode, once the minimal values are in Config, press nothing yet: go back and confirm that Setup is expected to show the four steps Configure, Authorize, Tunnel created and Tunnel connected; remotely managed mode should show the token notice. Then return to Config for a final check. Only when you are in your own environment, have finished the Home Assistant proxy configuration, and have a local fallback and a maintenance window, may you press Save & Restart; it really does write the options and restart the add-on, and only then does locally managed mode move on to the authorization in Chapter 5.

The minimal-change principle: let exactly one necessary hostname through the first time. Once authorization and the end-to-end test are done, weigh up additional hosts with Chapter 9.

Hard stops before you make a real change

  1. Keep secrets on trusted devices only

    The authorization URL, tunnel_token, cert.pem, the tunnel UUID, session cookies and full Logs must never go into a community post, an issue, a shared note or an unredacted screenshot. An ordinary configuration note records the mode and non-sensitive hostnames, nothing more.

  2. Do not make the Web GUI public

    You reach the Web GUI through Home Assistant Ingress and its sign-in protection, so there is no need to map the internal 8099 to the outside. The tunnel's public hostname should point at the service you intended, not at the Cloudflared admin page.

  3. Check that DNS will not hurt a service you already run

    Starting locally managed mode can overwrite the Cloudflare DNS records that match your external hostname or your additional hosts. Confirm one name at a time that it is free, and do not test with a company website, a mail name or a name the people you live with are using.

  4. Limit what you expose

    Create only hostnames with a clear owner and a clear purpose, and do not open a catch-all or wildcard DNS as a shortcut. A tunnel does not patch holes in your origin for you, and it does not replace a strong Home Assistant password and multi-factor authentication.

  5. Understand the two restart entrances

    Save & Restart in Config writes to Supervisor options first and then restarts; Restart Add-on on the Dashboard re-runs setup with the values already saved. Both interrupt the service, and neither is needed for planning or for a read-only check.

What is off-limits in the capture environment: do not press Save, Save & Restart, Restart Add-on, the authorization link or Copy link in the designated capture environment just to obtain a finished screen. States that need demonstrating are described in text and tables; we produce no real certificate and no DNS change.

Passing this chapter does not mean the tunnel is finished: as long as you can state the mode, where it is managed, the minimal route, the secrets and the hard stops, you can move on to Chapter 5. Only locally managed mode needs the Cloudflare authorization; remotely managed mode skips that local flow.

Common Setup pitfalls

  1. The configuration is blank and it says Tunnel stopped

    That is this fork's expected first state, not a broken add-on install. As long as Ingress and the four pages open, plan the real configuration first; do not use a fake hostname or token to clear the red status.

  2. You entered a hostname and Configure is still not complete

    Reload Config first and confirm the value really was written to Supervisor options. Typing it into the form without saving does not count; and if you did press Save & Restart, it has already written and restarted, so wait for the add-on to come back instead of pressing again.

  3. The four local steps are suddenly replaced by the token notice

    That means the current options contain tunnel_token. Do not simply clear it or paste in another token; first work out whether this is an existing remote-managed tunnel, and check the Cloudflare-side routes with whoever administers it.

  4. Stuck on Waiting for authorization

    Confirm that locally managed mode has every setting it needs and that the add-on has finished restarting, then look in Logs for a login request. If the authorization URL does not appear, do not assemble one yourself; follow Chapter 5 to check the network, the system time and the first prepare error.

  5. Certificate found, but no tunnel was created

    An existing certificate only completes the second step. Look in Logs for the first clear error after authorization, and check that the tunnel name is unique within the account, that your Cloudflare permissions are right and that the network works; deleting the certificate or authorizing over and over is not the first thing to try.

  6. Setup shows prepare failed

    Note the time it happened first, then take the smallest, already redacted error context from Logs. Schedule one restart only after you have fixed a clear configuration problem; restarting over and over only adds noise, and it can touch DNS again and again.

Setup FAQ

Does Setup store the data in a second configuration?
No. Supervisor options are the single source of truth; Setup mostly watches the mode, the certificate, the tunnel files and the connection progress, and Config is where you edit the options inside the Web GUI.
For a first install, should I choose locally or remotely managed?
The project DOCS list locally managed as the recommended flow. Choose remotely managed only when you already know Cloudflare Zero Trust, already have a remote-managed tunnel, and are clear about who is responsible for the token and the public hostnames.
Does remotely managed mode still have to finish the four Setup steps?
No. Once tunnel_token is set, Setup explains that the four local steps do not apply; the tunnel and the routes are managed in the Cloudflare dashboard, and the add-on's other local options are ignored.
Can I fill in the hostname first and decide the mode later?
You can plan it offline, but do not rush to save. The mode decides which of those fields get used; settling the boundary of responsibility first, then making one small and complete change, is safer than mixing the two afterwards.
Does Save & Restart just refresh Setup?
No. It writes to Supervisor options and restarts the add-on, so the Web GUI and the tunnel are interrupted for a while; locally managed mode may then go on to ask for authorization, create the tunnel and add a DNS route.
Why is there no finished screen from the capture environment?
Because a finished screen needs a real save, a real restart, a real Cloudflare authorization or a real tunnel state. Under the safety boundary for this guide we make none of those changes in the capture environment, and describe them from the current project documentation and source code instead.
