第 11 章

安全檢查與最小暴露

Tunnel 省掉路由器開埠，不代表每個 hostname 都該公開。你會逐層檢查 Cloudflare 帳號、DNS、Tunnel 路由、Zero Trust Access、Home Assistant 登入與 trusted proxy，讓每一層只擁有完成任務所需的權限。

為什麼要學這個

Cloudflare Tunnel 是由家中的 cloudflared 主動連向 Cloudflare，因此不用替 Home Assistant 在路由器開放入站連接埠。但「沒有開埠」只解決網路入口的一部分：DNS 仍決定外界能找到哪個名稱，Tunnel 路由決定名稱送去哪個內網服務，登入與 Access 政策則決定誰能進去。

把 NAS、路由器、監視器管理頁都放進 additional_hosts，就像為每個房間各做一扇外門。即使每扇門都有登入，也增加了要更新、監看與保護的入口。最安全的起點是只公開真的需要遠端使用的 Home Assistant hostname，其餘服務維持內網限定。

最小暴露：每新增一個 hostname 前，先回答「誰需要、何時需要、能否用 HA 功能取代、停止使用後由誰刪除 DNS 與路由」。答不出來就先不要新增。

六層邊界各管一件事

邊界負責什麼最小權限做法
網域註冊商與 Cloudflare 帳號網域與 zone 的控制權。使用個人帳號、唯一密碼與多重要素驗證（MFA）；管理者人數保持最少。
Cloudflare DNS把 hostname 指向 Tunnel。只留正在使用的記錄；移除路由後也檢查殘留 DNS。
Cloudflare Tunnel把 edge 收到的請求送往指定 origin。只建立必要 public hostname；避免不需要的 catch-all 與 wildcard。
Cloudflare Zero Trust Access在請求到達 origin 前套用身分政策。先建立明確允許對象與測試帳號；不要用過寬的網域或所有人規則。
Home Assistant使用者登入、MFA、權限與應用操作。每人獨立帳號，不共用管理者；為可用帳號啟用 MFA。
HA Ingress／Web GUI讓已登入 HA 的使用者開啟 add-on GUI。Web GUI 不另開 port；限制 HA 管理帳號，離開共用裝置時登出。
層層相加，不是互相取代：Cloudflare Access 不會替你管理 Home Assistant 使用者；Home Assistant MFA 也不會清理多餘 DNS 或 Tunnel 路由。每層都要各自檢查。
三種資料永遠不要分享：Cloudflare 授權網址、Tunnel token、日誌中的 secret。授權網址可能帶出一次性授權流程；remote-managed 的 tunnel_token 能讓持有者執行該通道；debug 日誌也可能包含環境祕密。不要貼到 issue、聊天室或截圖。

做一次唯讀安全盤點

  1. 列出真正需要的外部入口

    從 Cloudflared Web GUI 的 Config 唯讀抄下 external_hostname 與每個 additional host 的用途，不要抄 token。為每個名稱標記使用者、服務與保留理由；沒有負責人或用途的項目列入待移除，不要立刻按 Save。

  2. 對照 local-managed 或 remote-managed

    確認是否設定 tunnel_token。有 token 時是 remote-managed，add-on 文件指出其他本地選項會被忽略，路由應到 Cloudflare Dashboard 管理；沒有 token 的 local-managed 才由 add-on 依 options 建立設定與 DNS。不要在兩處同時猜著改。

  3. 核對 Cloudflare DNS 與 Tunnel 路由

    登入你自己的 Cloudflare 管理介面，以唯讀方式比對 DNS 記錄、Tunnel public hostname 與清單。正常結果是一個需要的 hostname 對到一個預期 origin，沒有舊名稱、拼字相近名稱、未知 wildcard 或不明 catch-all。

  4. 檢查帳號與 MFA

    在 Cloudflare 帳號與 Home Assistant 使用者設定中確認管理者是誰、是否仍需要權限，以及 MFA 是否啟用。選單名稱可能隨版本改變，請從帳號的 Security／Authentication 類頁面進入，不要依陌生網頁提供的捷徑輸入密碼。

  5. 檢查 Zero Trust Access 邊界

    如果你使用 Access，在 Zero Trust Dashboard 找到對應 self-hosted application，逐一讀取 Allow、Block 或其他政策。確認允許的是明確人員或群組，且有可用的復原管理者；若沒有部署 Access，不要把「有 Tunnel」誤寫成「已受 Access 保護」。

  6. 確認 Home Assistant proxy 設定沒有放太寬

    依 add-on 文件與 Home Assistant HTTP 官方文件核對 use_x_forwarded_for 與 trusted_proxies。只信任實際反向代理來源；不要為求方便信任所有位址。非標準安裝的來源範圍可能不同，應以 HA 日誌與你的網路設計確認。

本段是盤點，不是變更：本站教學環境製作期間只做唯讀查看，沒有 Save、Save & Restart、Authorize、Delete、DNS 或 Tunnel 變更。你在自己的 Web GUI 按 Save & Restart 會寫入 Supervisor options 並重啟 add-on，造成短暫中斷；刪 DNS、Access policy 或 token 也可能立即切斷遠端入口。先備份、確認本地登入與維護時段，再另行執行。

高風險選項怎麼判斷

選項／做法暴露範圍保守決策
external_hostname把 Home Assistant 放到指定外部名稱。只用一個清楚且專用的 hostname，保留 HA 登入與 MFA；確認路由器沒有另開 HA port。
additional_hosts每筆都可能把另一個內網服務送進 Tunnel。預設不加。服務本身沒有妥善登入、更新與稽核能力時不要公開。
catch_all_service未被前面規則匹配的請求會送往指定服務。一般家庭使用者保持空白；只有理解反向代理路由與預設拒絕行為時才規劃。
nginx_proxy_manager把未匹配流量交給 Nginx Proxy Manager add-on。不是「自動更安全」開關；沒有既有反向代理設計就不要啟用。
Wildcard DNS大量未明列子網域也可能解析到 Tunnel。避免使用；改為逐一建立必要名稱，盤點與移除都更清楚。
tunnel_token切換 remote-managed，其他本地 tunnel options 被忽略。視同密碼保存，只貼到受保護的 token 欄位；外洩時在 Cloudflare 端輪替。
post_quantum限制 Tunnel 使用 QUIC 與後量子混合金鑰交換，部分網路可能不通。不要把它當唯一安全開關；若要使用，先安排可回復測試。
移除路由不一定等於清掉 DNS：add-on 文件明確提醒，從 additional_hosts 刪除 hostname 後，該路由不再提供服務，但 Cloudflare DNS 記錄需要人工檢查並刪除。兩邊都完成才算收尾。

最小暴露檢查表

檢查通過標準未通過時
路由器沒有為 Home Assistant、Web GUI 或內網 additional host 建立公網入站 port forwarding。先確認沒有其他遠端方案依賴，再排維護時段移除。
Cloudflare 帳號管理者名單正確、使用唯一密碼、MFA 已啟用、離職或停用帳號已撤權。先保留至少一個可用管理者，再調整權限。
DNS每筆代理 hostname 都有用途；沒有殘留、未知或過寬 wildcard。比對 Tunnel 與使用紀錄後再刪，並記錄變更。
Tunnel 路由origin 指向預期服務與連接埠；沒有路由器、NAS 管理頁等不必要入口。先確保本地管理可用，再做最小化。
Zero Trust Access若宣稱有 Access，確實存在對應 application 與最小 Allow policy，並已用允許及不允許帳號測試。在政策驗收前，不要把 Tunnel 視為已受 Access 身分保護。
Home Assistant每人獨立帳號；不需要管理權的日常帳號不是管理者；MFA 已設定。先建立並驗證替代管理者，避免把自己鎖在外面。
trusted proxy只列必要 proxy 網路或位址，沒有 0.0.0.0/0 之類的全網信任。依官方 HTTP 文件與 HA 日誌修正，並驗證真實來源 IP。
祕密資料token、授權網址、憑證與敏感日誌不在筆記、截圖、備份說明或公開 issue。立即刪除公開副本，並依資料類型撤銷或輪替。
每季再做一次：家庭成員、裝置與臨時服務都會變。每三個月及每次新增 hostname 後重跑清單，比出事後回想設定可靠。

從允許與拒絕兩邊驗收

  1. 確認本地復原入口

    在家中網路用本地網址登入 Home Assistant，確認至少一位授權管理者可操作。這一步讓外部政策設錯時仍有回復路徑。

  2. 確認預期 hostname

    手機關閉 Wi-Fi，逐一測試清單上應保留的 hostname。Home Assistant 名稱只能到 HA 或你設計的 Access 流程，不可誤送到其他內網服務。

  3. 確認不該存在的名稱

    挑一個已移除或從未設定的測試子網域，確認它不會因 wildcard 或 catch-all 意外顯示內網服務。不要用掃描工具大量探測。

  4. 驗收身分政策

    若使用 Cloudflare Access，以一個允許帳號與一個不在允許範圍的帳號分別測試。前者通過預期驗證，後者應被 Access 擋下；再確認 HA 自己仍要求登入。

  5. 驗收來源位址與日誌

    登入後到 Home Assistant 查看相關安全事件或日誌，確認沒有反向代理錯誤與重複登入異常。若所有連線都被當成不合理來源，回頭檢查 proxy 設定，不要放寬成信任全網。

  6. 驗收沒有新增暴露

    確認路由器 port forwarding 沒有因本次教學變更、Config 沒有未核准項目、debug 已關閉，並把日期與通過項目寫進維護紀錄，不放任何 secret。

通過定義：該進的人能走到正確服務，不該進的人與不存在的名稱被擋下，而且本地管理仍可用。只測「我自己能登入」會漏掉過度允許。

安全設定常見卡關

  1. 啟用 Access 後自己也進不去

    先用本地 HA 入口確認服務正常，再由 Cloudflare 管理者檢查 application hostname、policy 順序、允許身分與登入方法。不要為了恢復而建立「所有人皆可」的永久 Allow；先用明確管理者做最小修正。

  2. 刪除 additional host 後 DNS 還在

    這符合 add-on 文件提醒：停止提供路由不會自動替你刪除既有 DNS。到 Cloudflare DNS 比對該名稱，確認沒有其他用途後手動移除，再從外部驗收不再到達服務。

  3. 設了 tunnel_token，Config 其他項目不生效

    remote-managed 模式下，其他 local-managed options 會被忽略。請到 Cloudflare Dashboard 管理 public hostname 與 origin；不要同時在兩邊反覆 Save。token 不可貼進日誌、客服對話或截圖。

  4. HA 顯示來自反向代理的請求被拒絕

    依 Home Assistant HTTP 文件與 add-on 文件檢查 use_x_forwarded_for、trusted_proxies 和 YAML 位置。標準 HAOS add-on 文件提供其 Docker 網路範例；非標準安裝要用實際來源確認，不能照抄更大的範圍。

  5. 移除 wildcard 後部分服務失效

    先查出哪些 hostname 偷偷依賴 wildcard，逐一決定保留或停用，必要的改成明確 DNS 與明確 Tunnel 路由。復原 wildcard 雖快，卻會重新擴大暴露；只有在已核准的短暫回復計畫中使用。

疑似 token 或授權資料外洩：不要只刪貼文。立即在 Cloudflare 端撤銷或輪替相應憑證／token，檢查 Tunnel connectors、帳號活動與 DNS 是否有未知變更，再更新 add-on 受保護欄位並驗收。

常見問題

用了 Cloudflare Tunnel，還需要 Home Assistant MFA 嗎？
需要。Tunnel 負責網路路徑，不是 Home Assistant 帳號的第二因素。HA MFA、每人獨立帳號與最小管理權仍要保留；若另加 Cloudflare Access，則是再多一層，不是替代。
Web GUI 的內部 8099 port 需要在路由器開放嗎？
不需要。WOOWTECH 文件說明 Web GUI 透過 Home Assistant Ingress 提供，不額外暴露 port，並由 HA 登入保護。請不要自行建立路由器 port forwarding。
hostname 本身算祕密嗎？
公開 DNS 名稱通常可以被外界發現，不能當成密碼。你仍應避免在不必要的截圖與日誌中散布住家識別名稱；真正必須保密的是 token、授權網址、憑證與 secret。
Cloudflare Access 是不是一定要開？
它是可加入的額外身分邊界，是否適用取決於你的登入方式與使用者。沒有完成 policy、允許與拒絕測試前，不要宣稱已受 Access 保護；即使有 Access，HA 登入與 MFA 仍不可省略。
為什麼不建議公開路由器或 NAS 管理頁？
Tunnel 雖不開入站 port，仍把應用入口帶到網際網路邊界。老舊管理頁可能缺少 MFA、更新慢或權限過大。遠端需求應優先使用專用安全方式，而不是把所有內網管理面都列入 additional_hosts。
